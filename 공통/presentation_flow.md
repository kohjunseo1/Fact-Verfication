## 1. 주제 소개: Fact Verification

**슬라이드 1-1. Fact Verification이란**
- 주어진 문장(claim)이 사실인지 판단하는 작업. 문장 자체의 그럴듯함이 아니라 **외부 근거와 일치하는지**를 검증한다.
- 사람이 팩트체크하는 과정을 그대로 옮긴 구조: 근거 찾기 → 근거와 대조 → 판정
- 예시 한 줄 (가이드 2.1의 Krøyer / Zahrtmann 예시 사용)

**슬라이드 1-2. 왜 multi-hop이 어려운가**
- multi-hop verification은 여러 문서를 거쳐 정보를 연결해야 한다 → 추론 능력과 정보 연결 능력을 동시에 요구
- Bridge 예시: "The Assignation을 쓴 극작가는 1668년 계관시인이 되었다"
  - 두 번째 문서(John Dryden)의 이름이 claim에 **없다**. 첫 문서를 읽어야 다음 문서를 알 수 있다.
- 메시지: "검색 한 번으로는 두 번째 근거를 찾을 수 없다"가 이 과제의 핵심 난제

## 2. 과제와 비즈니스 문제

**슬라이드 2-1. 주어진 과제**
- 사용자 질문(query)에 관련된 hop을 탐색하고, 이를 바탕으로 응답하는 구조 구축
- 참고: FEVER (single-hop, 3-class) / 학습 데이터: HoVer (multi-hop, 2-class)
- 난이도 5/5. 우리는 multi-hop을 유지하되 **2-hop으로 범위를 고정**

**슬라이드 2-2. 해결하려는 문제**
- LLM은 수준이 매우 높아졌지만, 동작 원리상 사실과 다른 내용을 그럴듯하게 만들어내는 할루시네이션 문제가 남아 있다.
- 그래서 생성 결과를 근거와 대조해 검증하는 단계가 여전히 필요하고, fact verification이 그 역할을 한다.
- 특히 여러 사실을 연결한 문장은 겉보기엔 자연스러워도 연결 고리 하나만 틀리기 쉬워, multi-hop 검증이 필요하다.
- 이어지는 지표 연결: **NOT_SUPPORTED recall = 사실이 아닌 문장을 놓치지 않는 비율**

## 3. 데이터: HoVer와 2-hop

**슬라이드 3-1. HoVer 데이터셋**
- HotpotQA 질문-답을 claim으로 변환, 2~4-hop, 라벨 SUPPORTED / NOT_SUPPORTED (FEVER와 달리 NEI 없음)
- 각 claim에 정답 근거 `supporting_facts` = (위키 제목, 문장 번호) 목록
- 검색 코퍼스: HoVer가 배포한 2017-10-01 위키 첫 단락 DB (약 520만 문서), CC BY-SA 4.0

| num_hops | 공식 train | 공식 dev |
|---|---|---|
| 2 | 9,052 | 1,126 |
| 3 | 6,084 | 1,835 |
| 4 | 3,035 | 1,039 |

**슬라이드 3-2. 우리의 분할과 2-hop 선택 이유**
- 공식 train 2-hop을 `hpqa_id` 그룹 기준 9:1로 분할 → train 8,166 / val 886. 같은 HotpotQA 질문에서 나온 claim이 train과 val에 나뉘지 않게 함
- 공식 dev 2-hop 1,126건 = test (최종 보고에만 사용)
- 2-hop을 고른 이유: 기간(1주일) 안에 검색·선택·판정 전 단계를 끝까지 만들고 측정하기 위해. 3·4-hop 학습은 일부 팀원이 시도(고준서, 황혜림)했지만 평가는 2-hop 공통

**슬라이드 3-3. 데이터에서 발견한 함정**
- 라벨 분포 반전: train/val SUPPORTED 72% vs test 46% → accuracy만 보면 안 됨, macro-F1 병행 + 클래스 가중치
- 유니코드: 정답 제목은 NFC, 위키 DB는 NFD → 같은 문서를 다른 문서로 비교하던 버그 (수정 후 recall@20 0.580 → 0.602)
- 문장 번호 정합성: CoreNLP 문장 분리 결과와 HoVer 문장 번호가 어긋나는 claim 존재 (고준서 감사, 황혜림은 덤프 원본 문장으로 회피)
- (선택) 분할 누수: 무작위 분할 시 val의 49.9%가 train과 같은 `hpqa_id`

## 4. 팀 베이스라인 4종 한눈에

**슬라이드 4-1. 공통 프레임과 차이**

```
claim → ① 1-hop 문서 후보 → ② bridge 문서 탐색 → ③ 근거 문장 선택 → ④ SUPPORTED / NOT_SUPPORTED
```

| | 고준서 | 이상민 | 한기선 | 황혜림 |
|---|---|---|---|---|
| 핵심 아이디어 | 학습 RoBERTa + k-hop beam search | 개체명(NER) → 제목 검색, 경량 모델 | TF-IDF 재정렬 + 학습된 hop-2 검색기 | 위키 하이퍼링크 그래프 탐색 |
| bridge 탐색 | 본문 속 제목 언급, 경로 전체 문맥 | spaCy 개체 → SQLite 제목 검색 | 본문 속 제목 언급 | 실제 링크 그래프 |
| 판정기 | roberta-base | MiniLM-L6 | roberta-base | bert-base (논문 레시피) |
| 강점 | 3/4-hop 일반화, 누수 관리 | 설명 가능, 가벼움 | 2-hop 최고 수치, 상·하한 측정 | 데이터 분석, 전체 hop 실측, 속도 |

- 메시지: "실패의 85%가 두 번째 문서를 놓친 경우" → ② bridge 탐색을 어떻게 푸느냐가 네 명의 가장 큰 차이
- 최종 수치는 [compare_baselines.py](compare_baselines.py)로 같은 규칙 채점 후 채워 넣는다 (현재 자기 보고값만 있음)

## 5. 평가 지표와 논문 대비 결과

**슬라이드 5-1. 지표 설계**

| 단계 | 지표 | 의미 |
|---|---|---|
| 문서 검색 | Recall@k (all-hit) | 정답 문서 2개가 모두 상위 k 안에 든 claim 비율. 2-hop의 실질 성공 조건 |
| 문장 선택 | all_gold@k, evidence EM/F1 | 정답 문장을 다 찾았나 / 논문 지표와 맞춘 값 |
| 판정 | Accuracy, Macro-F1, NOT_SUPPORTED recall | 분포 차이 때문에 macro-F1 병행. NS recall은 할루시네이션을 놓치지 않는 비율 |
| 전체 | **HoVer score** | 라벨이 맞고, 정답 문서마다 근거 문장을 하나 이상 찾았을 때만 정답. "올바른 근거를 보고 맞혔는가" |

- HoVer score가 필요한 이유: claim만 보고도 62%를 맞힌다 → 라벨 정확도만으로는 근거 기반 판정인지 알 수 없음
- 공식 채점 규칙: 처음 등장한 순서로 앞 k+1개 문서, 문서당 앞 2문장만 인정 (공식 스크립트 링크가 404라 사이트 설명대로 직접 구현)

**슬라이드 5-2. 하한선과 상한선으로 보는 실험 설계**
- 하한선: claim-only (근거 없이 판정) / 상한선: oracle (정답 근거를 직접 입력)
- 모든 개선을 이 사이의 어디에 있는지로 설명 → 병목이 검색인지 판정기인지 판별

확인 방법: 논문 수치는 arXiv HTML 원문(2011.03088v2) Table 3~8과 본문에서 직접 대조했다. 열 순서는 2 / 3 / 4-hop / 전체다. 우리 수치는 각 노트북의 저장된 출력과 git 기록에서 확인했다.

확인하면서 알게 된 점:
- 논문에서 **hop별 값이 있는 것은 Table 3~6뿐**이다. 전체 파이프라인 결과(Table 7)와 test 결과(Table 8)는 hop 구분 없이 전체만 보고한다.
- Table 3(TF-IDF)은 dev 중 **SUPPORTED claim만** 평가했다고 캡션에 적혀 있다. 2-hop SUPPORTED는 521건이다.
- 논문 모델은 2/3/4-hop train 전체로 학습했고, 2-hop 열은 평가만 2-hop으로 나눈 것이다. 우리는 2-hop만으로 학습했다.
- test HoVer 15.32(Table 8)는 BERT+Retr가 아니라 **BERT+Gold** 모델의 값이다. 그래서 dev 14.5와 짝지으면 안 된다.
- 우리 v2.2 수치(acc 0.755, HoVer 0.591)는 가이드에만 기록되어 있고, 노트북 출력은 v3 실행(acc 0.729, HoVer 0.579)으로 덮어써졌다. 발표에는 git에 출력이 남은 v2.1 값(acc 0.755, HoVer 0.581)을 쓰거나, v2.2를 다시 실행해 출력을 남긴다.

발표 멘트 포인트:
1. **2-hop 같은 조건에서 직접 비교 가능한 것은 claim-only와 oracle뿐**이다. 상한선은 논문과 거의 같고(80.0 vs 79.8), 우리 파이프라인(75.5)은 그 상한의 94%까지 왔다.
2. 문서 검색은 같은 TF-IDF에서 출발했지만, multi-hop 검색으로 top-5 all-hit를 39.7% → 84.2%로 올렸다. 논문 구조는 TF-IDF top-20 안에서 순서만 바꾸므로 이 천장(우리 측정 약 60%)을 넘을 수 없다.
3. 전체 파이프라인 정확도와 HoVer score는 논문이 전체 hop 값만 보고하므로 나란히 놓으면 안 된다. HoVer score는 hop이 늘수록 급락한다(황혜림 실측: 2-hop 35.3 / 전체 17.2). 논문 전체 hop 수치(dev 14.5)나 리더보드(공식 15.32, Baleen 57.53)와 우리 2-hop 수치를 같은 표에 둘 때는 **"평가 범위 다름"을 슬라이드에 명시**한다.
4. 전체 hop에서 논문과 공정 비교한 결과가 필요하면 황혜림 결과(전체 dev 4,000건, HoVer 17.2 vs 논문 14.5, claim당 151ms vs 172ms)를 보조 슬라이드로 쓴다.

발표 전 채울 것:
- [ ] test 문서 EM/F1(top-5 문서 기준), 문장 EM/F1(2문장 제출)을 논문 정의로 계산해 표의 △/✗ 칸 교체
- [ ] TF-IDF Hit@5/100을 2-hop SUPPORTED 521건만으로 다시 계산 (Table 3과 같은 범위)
- [ ] v2.2를 발표 수치로 쓰려면 다시 실행해 노트북 출력을 남기기 (현재는 가이드 기록만 있음)
- [ ] v2.2와 v3 중 제출 버전 확정 (v3는 검색 87.5%로 올랐지만 판정 0.729로 하락, seed 재확인 필요)
- [ ] 가능하면 3 seed 평균 ± 표준편차 (재학습 편차 macro-F1 ±0.01, HoVer ±0.02)

## 6. 대표 파이프라인 상세: 한기선 (학습된 hop-2 문서 검색기)

**선정 이유 (슬라이드 6-0, 한 줄씩)**
- 2-hop test에서 실측한 수치가 가장 높고, 노트북 출력과 버전 기록으로 검증 가능
- 논문 베이스라인과 같은 "문서 검색 → 문장 선택 → 검증" 골격이라 **차이점만 떼어 설명하기 쉽다**
- 하한·상한·단계별 천장을 모두 재서 "병목이 어디서 어디로 옮겨갔는가"를 숫자로 보여줄 수 있다
- k8s 데모(한기선/demo)가 있어 시연 가능

> 대안: 논문과 같은 판정기 레시피로 전체 hop을 비교하려면 황혜림, 3/4-hop 확장성을 강조하려면 고준서 파이프라인. 고준서는 실측 결과가 나와야 선택 가능.

**슬라이드 6-1. 전체 흐름**

```
claim
 ① TF-IDF top-100 (HoVer 저자 제공, 학습 없음)
 ② roberta 문서 재정렬 → 상위 2개 = hop 1
 ③ hop 2 후보 = claim과 hop 1 본문에 언급된 위키 제목 (제목 사전 약 480만 개)
 ④ roberta hop-2 채점: (claim | hop1 제목+본문, 후보) → 경로 점수 P(a) × P(c|a) → 문서 top-5
 ⑤ CoreNLP 문장 분리 → roberta 문장 선택 → top-5 문장
 ⑥ roberta 검증기 (claim, 문장 5개) → SUPPORTED / NOT_SUPPORTED
```

- 학습 모델 4개(②④⑤⑥), 모두 roberta-base에서 각각 fine-tuning. 학습 없는 단계는 ①③과 문장 분리

**슬라이드 6-2. 왜 hop-2 검색기를 만들었나 (병목 추적)**
- v1(논문 구조 그대로): 근거를 다 찾은 claim은 0.783으로 상한에 가까운데, 42%는 첫 단계에서 정답 문서를 놓침
- 실패 claim의 85%가 "문서 하나는 찾고 나머지 하나를 놓침" → 찾은 문서를 단서로 다음 문서를 찾는 구조가 필요
- 결과: 문서 all-hit@5 57.7% → 84.2%, 문장 all_gold@5 46.3% → 69.9%, HoVer 0.362 → 0.553

**슬라이드 6-3. 학습 데이터 설계 (핵심 디테일)**
- 검색 모델(②④⑤): 정답을 후보에 일부러 넣어 학습 (teacher forcing). hop-2는 정답 문서 2개를 번갈아 hop 1 자리에 넣어 양방향 학습
- 검증 모델(⑥): 정답 근거가 아니라 **파이프라인이 실제로 고른 근거**로 학습 → 추론 때와 같은 잡음 조건
- 클래스 가중치(NS 1.77 / S 0.70) + val macro-F1 최고 epoch 선택 → train/test 분포 반전 대응

**슬라이드 6-4. 버전별 성능 변화 (test 2-hop)**

| 버전 | 바뀐 점 | 문서 all-hit@5 | acc | macro-F1 | HoVer(공식 규칙) |
|---|---|---|---|---|---|
| claim-only | 하한선 | – | 0.622 | 0.620 | – |
| v1 | 논문 구조 (TF-IDF top-20 → 재정렬) | 57.7% | 0.737 | 0.736 | – |
| **v2.2** | multi-hop 검색 + 재학습 | 84.2% | **0.755** | **0.755** | **0.591** |
| oracle | 상한선 | – | 0.800 | 0.800 | – |

**슬라이드 6-5. 병목은 이제 판정기 (결과 해석)**
- HoVer 분해: evidence_ok 0.762 → 근거를 못 찾아 잃은 몫 23.8%p, 근거는 맞았는데 라벨을 틀린 몫 17.1%p
- 오류는 NOT_SUPPORTED → SUPPORTED 쪽에 몰림 (NS recall 약 63%) → 틀린 문장을 사실로 통과시키는, 검증 단계에서 가장 치명적인 오류
- 정답 근거를 넣어도 0.80 → roberta-base 판정기 자체의 천장이 다음 과제

## 7. 논문과의 주요 차이점

| 항목 | HoVer 논문 베이스라인 | 우리 파이프라인 | 효과 / 이유 |
|---|---|---|---|
| 문서 간 연결 | 문서를 독립적으로 채점 | **hop 1 문서를 조건으로 hop 2 문서를 채점** (경로 점수) | 가장 큰 차이. all-hit@5 57.7 → 84.2% |
| hop 2 후보 | 없음 (TF-IDF 후보 안에서만) | 위키 제목 언급으로 TF-IDF 밖 문서까지 후보 확장 | TF-IDF top-20 천장(약 60%) 돌파 |
| 문서 선택 | 확률 0.5 이상, 최대 5개 (가변) | 경로 점수 상위 5개 (고정) | 2-hop은 정답이 정확히 2개라 고정 k가 안정적 |
| 문장 선택 | 확률 0.3 이상 (가변) | 상위 k개 고정, 제출 개수 n은 val로 선택 | 공식 채점 규칙에 맞춰 튜닝 |
| 모델 | BERT-base, 판정 길이 200 | roberta-base, 판정 길이 384 | 근거 5문장이 잘리지 않게 |
| 불균형 처리 | 없음 | 클래스 가중치 + macro-F1 기준 모델 선택 | train 72% / test 46% 분포 반전 대응 |
| 학습·평가 범위 | 전체 hop, 공식 train/dev | 2-hop 전용, `hpqa_id` 그룹 분할 | 기간 내 완주, 누수 방지 |
| 채점 | 공식 스크립트 | 공식 스크립트 비공개(404) → 사이트 규칙대로 재구현 | 다른 팀원 결과도 같은 채점기로 비교 |

## 8. 한계와 프로젝트 이후 시도해볼 것

**슬라이드 8-1. 한계 (솔직하게)**
- 2-hop 전용 설계 (hop 2까지만 다룸), 3/4-hop 미측정
- 판정기 천장 0.80, NS recall 낮음
- seed 1개 결과 위주, 팀원 간 수치는 같은 채점기로 재검증 전
- 공식 train/dev에 겹치는 77개 `hpqa_id` 그룹 미격리 (고준서만 격리)

**슬라이드 8-2. 다른 팀원 파이프라인에서 가져올 것**

| 가져올 것 | 출처 | 기대 효과 |
|---|---|---|
| 하이퍼링크 그래프 이웃을 hop-2 후보에 합치기 | 황혜림 | 2-hop 정답 쌍의 87.4%가 직접 링크로 연결. 제목 언급 방식이 놓친 후보 보충 |
| 2-fold 교차 예측으로 판정기 학습 근거 만들기 | 황혜림 | train 근거 품질을 dev와 맞춰 판정기 과신 방지 |
| hybrid 문장 선택 (확률 기준 + 문서당 1문장 구제) | 황혜림 | 근거 정밀도 +11%p, 정확도 상승 |
| 덤프 원본 문장 사용 | 황혜림 | CoreNLP 문장 번호 불일치 문제 원천 제거 |
| k-hop beam search + 경로 전체 문맥 | 고준서 | 같은 코드로 3/4-hop 확장 |
| 공식 train/dev 겹침 그룹 격리, 설정 fingerprint, pytest | 고준서 | 재현성과 누수 관리 |
| 개체 기반 explicit hop (어떤 개체로 넘어갔는지) | 이상민 | 판정 근거 설명력 (서비스 UI에 경로 표시) |
| hop-2 중복 제거 후 다음 후보 보충, threshold 탐색 | 이상민 | 근거 다양성, NS recall 조정 |
| 경량 모델(MiniLM) 서빙 구성 | 이상민 | 지연시간·비용 절감 (distillation 대상) |

**슬라이드 8-3. 고려해볼 아키텍처와 기술**

판정기 (현재 병목)
- NLI로 사전학습된 모델에서 시작: DeBERTa-v3-large (MNLI/FEVER fine-tuned), roberta-large-mnli. FEVER → HoVer 순차 전이학습
- 근거별로 따로 추론 후 합치는 evidence aggregation (문장 간 관계를 보는 graph/attention 기반 aggregator)
- NS recall 기준 threshold 보정, NOT_SUPPORTED 변형 유형(황혜림 `claim_mutations.py`)으로 hard negative 생성

검색
- Dense multi-hop retrieval: MDR(질의 + hop1 문서로 다시 dense 검색), Baleen(hop마다 근거 압축 후 다음 질의, 리더보드 57.53)
- Hybrid 1차 검색: BM25/TF-IDF + dense(bi-encoder) 결합으로 TF-IDF top-100 천장(77.5%) 해소
- ColBERT 계열 late interaction으로 재정렬 비용 절감

LLM 활용
- ProgramFC/QACheck 방식 claim 분해: LLM이 하위 질문으로 쪼갠 뒤 각각 검색·답변·종합 (학습 불필요, 설명력 높음, 대신 비용·지연 큼)
- 하이브리드 운영: 소형 파이프라인이 먼저 판정 → 확신도가 낮은 claim만 LLM 검증 또는 사람 검수로 넘기는 selective prediction / abstain
- LLM으로 생성한 판정 근거를 소형 모델로 distillation

평가와 운영
- 3 seed 평균, paired bootstrap 유의성, 사람 평가 50~100건(근거 충분성)
- 확률 보정(calibration)과 "검수 필요" 구간 설정 → 확신이 낮은 판정만 사람이 다시 확인
- 서빙: k8s 데모 확장, ONNX/양자화로 claim당 지연시간 단축
