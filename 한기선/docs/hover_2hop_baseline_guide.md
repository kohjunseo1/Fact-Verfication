## 1. 한눈에 보기

### 무엇을 만들었나

주장(claim) 하나를 받아서 위키피디아에서 근거 문장을 찾고, 그 주장이 **맞는지(SUPPORTED) 틀린지(NOT_SUPPORTED)** 판정하는 시스템이다. HoVer 데이터셋 중 **근거 문서가 2개 필요한 2-hop claim**만 다뤘다.

```
claim ──▶ [문서 검색] ──▶ [문장 선택] ──▶ [주장 검증] ──▶ SUPPORTED / NOT_SUPPORTED
           520만 문서 →      문서 5개의 →      claim + 문장
           문서 5개          문장 k개          → 참/거짓
```

### 결과 요약 (test)

| 구분 | 내용 | accuracy | macro-F1 | HoVer score |
|---|---|---|---|---|
| 기준선 | 항상 SUPPORTED라고 답하기 | 0.463 | 0.316 | - |
| **하한선** | claim만 보고 판정 (근거 없음) | 0.622 | 0.620 | - |
| **베이스라인** | 검색 → 문장 선택 → 검증 (k=5) | **0.737** | **0.736** | **0.362** |
| **상한선** | 정답 근거를 직접 넣고 판정 | 0.800 | 0.800 | - |
| **Multi-hop** | 08 hop 1 → hop 2 검색 → 문장 선택 → 검증 (k=5) | **0.763** | **0.763** | **0.570** |

**Multi-hop 효과**: 문서 recall@5 56.7% → 83.6%, 문장 all_gold@5 46.3% → 70.8%, **HoVer score 0.362 → 0.570**, macro-F1 0.736 → 0.763. 자세한 내용은 [9.5](#95-08-노트북-결과).

### 핵심 결론 3가지

1. **근거는 확실히 도움이 된다.** claim만 볼 때 0.620 → 근거를 검색해 넣으면 0.736.
2. **병목은 검색, 특히 첫 단계(TF-IDF 후보)다.** 근거를 다 찾은 claim은 검증 성능이 0.783으로 상한선(0.800)에 가깝다. 반면 42%의 claim은 첫 단계에서 이미 정답 문서를 놓친다.
3. **놓치는 이유는 "두 번째 문서" 문제다.** 실패한 claim의 85%가 문서 하나는 찾고 나머지 하나를 놓친 경우다. 그래서 찾은 문서를 단서로 다음 문서를 찾는 **multi-hop 검색**을 만들었고, 문서 recall@5가 56.7%에서 83.6%로 올랐다.

## 2. 문제 정의: 사실 검증과 HoVer

### 2.1 사실 검증 (Fact Verification)

주장 하나가 주어졌을 때 (1) 근거를 찾고 (2) 근거에 비추어 주장이 맞는지 판정하는 작업이다. 사람이 팩트체크하는 과정을 그대로 옮긴 것이다.

```
주장: "Peder Severin Krøyer는 Kristian Zahrtmann과 함께 자연주의를 지지했다"
  ↓ 근거 찾기
근거: "Zahrtmann은 Krøyer, Philipsen과 함께 ... 자연주의와 사실주의를 지지했다"
  ↓ 판정
SUPPORTED
```

### 2.2 HoVer 데이터셋

- **HoVer** (Jiang et al., 2020, *HoVer: A Dataset for Many-Hop Fact Extraction And Claim Verification*)
- HotpotQA(다중 문서 질의응답 데이터)의 질문-답을 주장 문장으로 바꿔서 만들었다.
- 라벨은 **2개**다: `SUPPORTED`, `NOT_SUPPORTED`. FEVER처럼 "정보 부족(NEI)" 라벨이 없다.
- 각 claim에는 정답 근거 `supporting_facts`가 (위키 문서 제목, 문장 번호) 목록으로 달려 있다.

### 2.3 Hop이란

**hop = claim을 검증하는 데 필요한 위키 문서 수**다. 데이터의 `num_hops` 값은 `supporting_facts`에 나오는 서로 다른 문서 수와 18,171건 전부에서 정확히 일치했다.

| num_hops | 근거 문서 수 | train 개수 |
|---|---|---|
| 2 | 2 | 9,052 |
| 3 | 3 | 6,084 |
| 4 | 4 | 3,035 |

hop이 늘수록 여러 문서를 연결해서 추론해야 하므로 어려워진다.

### 2.4 2-hop claim의 두 가지 유형

| 유형 | 예시 | 특징 |
|---|---|---|
| **Bridge (연결형)** | "The Assignation을 쓴 극작가는 1668년 계관시인이 되었다" | 첫 문서(The Assignation)를 읽어야 두 번째 문서(John Dryden)의 이름을 알 수 있다. **두 번째 문서 이름이 claim에 없다** |
| **Comparison (비교형)** | "José Echegaray와 Graham Swift 중 직업 범위가 더 넓은 사람은 Echegaray다" | 두 문서 이름이 claim에 다 나온다. 각 문서를 읽고 비교한다 |

Bridge 유형이 검색을 어렵게 만드는 핵심이다. 이유는 [9장](#9-multi-hop-검색-상세)에서 자세히 다룬다.

## 3. 전체 플로우

### 3.1 파이프라인

```
                         ┌──────────────────────────────────────────┐
claim ─────────────────▶ │ 3단계  문서 검색                          │
                         │  ① TF-IDF로 위키 520만 문서 → top-100     │  (저자 제공, 학습 없음)
                         │  ② 상위 20개를 roberta로 재정렬 → top-5   │  (학습)
                         │  ③ [3-B] hop 1 → hop 2 검색 (multi-hop)   │  (학습, 08 노트북)
                         └──────────────────┬───────────────────────┘
                                            ▼
                         ┌──────────────────────────────────────────┐
                         │ 4단계  문장 선택                          │
                         │  top-5 문서의 모든 문장(약 20개)          │
                         │  → roberta가 근거 확률 → top-k 문장       │  (학습)
                         └──────────────────┬───────────────────────┘
                                            ▼
                         ┌──────────────────────────────────────────┐
                         │ 5단계  주장 검증                          │
                         │  (claim, top-k 문장) → roberta            │  (학습)
                         │  → SUPPORTED / NOT_SUPPORTED              │
                         └──────────────────────────────────────────┘
```

원본 HoVer 논문의 베이스라인 구조(문서 검색 → 문장 선택 → 검증)를 그대로 따랐다. 모델은 BERT 대신 **roberta-base**를 썼다.

### 3.1.1 단계별 모델과 Fine-tuning 여부

**Fine-tuning** = 다른 곳에서 사전학습된 모델을 가져와 **우리 HoVer 데이터로 추가 학습**하는 것. 학습 가능한 모델이 아닌 도구(통계 계산, 규칙)는 fine-tuning 대상이 아니다.

| 순서 | 단계 | 어디서 (노트북) | 무엇을 쓰나 | 종류 | 출발점 | Fine-tuning |
|---|---|---|---|---|---|---|
| ① | 1차 문서 검색 | `02`에서 결과 다운로드 | **TF-IDF** (DrQA 구현) | 통계 기반 검색 | HoVer 저자가 계산해 공개한 top-100 | ❌ 학습하는 모델이 아님. 결과 파일만 사용 |
| ② | 문서 재정렬 | `05_doc_retrieval` | **roberta-base** + 분류층 | 크로스 인코더 | Hugging Face `roberta-base` (Meta 사전학습) | ✅ train 약 16만 쌍, 1 epoch |
| ③ | hop 2 후보 생성 | `08_multihop_retrieval` | **위키 제목 매칭** | 규칙 (정규표현식 + 제목 사전) | 우리가 작성 | ❌ 규칙 |
| ④ | hop 2 점수 | `08_multihop_retrieval` | **roberta-base** + 분류층 | 크로스 인코더 | Hugging Face `roberta-base` | ✅ train 약 13만 쌍, 1 epoch |
| ⑤ | 문장 나누기 | `06_sent_retrieval` (`02`에서도 사용) | **Stanford CoreNLP** 4.6.0 (`stanza`로 실행) | 규칙 기반 문장 분리 | Stanford 배포판 | ❌ 규칙 |
| ⑥ | 문장 선택 | `06_sent_retrieval` | **roberta-base** + 분류층 | 크로스 인코더 | Hugging Face `roberta-base` | ✅ train 약 16만 쌍, 1 epoch |
| ⑦ | 주장 검증 | `07_end_to_end` | **roberta-base** + 분류층 | 크로스 인코더 | Hugging Face `roberta-base` | ✅ train 8,166 claim, 3 epoch, 클래스 가중치 |

비교 기준용 모델(실제 추론 흐름에는 들어가지 않음):

| 단계 | 어디서 | 무엇을 쓰나 | Fine-tuning |
|---|---|---|---|
| 하한선 (claim-only) | `03_claim_only` | roberta-base + 분류층, 입력은 claim만 | ✅ train 8,166 claim, 3 epoch |
| 상한선 (oracle) | `04_oracle` | roberta-base + 분류층, 입력은 claim + 정답 근거 | ✅ train 8,166 claim, 3 epoch, 클래스 가중치 |

**정리**
- 학습하는 모델은 **②④⑥⑦ 네 개**이고, 모두 **같은 `roberta-base`에서 각각 따로 출발**해 다른 일을 배운다. 서로 가중치를 공유하지 않는다.
- 각 모델의 **분류층(768→768→2)은 무작위로 새로 만들고**, 몸통(인코더 12층)은 사전학습 가중치에서 시작해 **함께 조금씩 수정**한다(전체 fine-tuning, lr 2e-5).
- ①③⑤는 학습이 없다. ①은 미리 계산된 결과, ③⑤는 정해진 규칙이다.
- 다른 곳에서 이미 재정렬이나 사실 검증용으로 학습된 모델(예: MS MARCO 재정렬 모델, MNLI 모델)은 쓰지 않았다. 모두 범용 사전학습 모델인 `roberta-base`에서 시작했다.

### 3.1.2 Fine-tuning한 4개 모델의 학습 비교

**공통 설정** (네 모델 모두 같음)

| 항목 | 값 |
|---|---|
| 출발 모델 | `roberta-base` + 새 분류층 (768→768→2) |
| 손실 함수 / 옵티마이저 | cross-entropy / AdamW (Trainer 기본값) |
| learning rate / warmup / weight decay | 2e-5 / 전체 스텝의 10% / 0.01 |
| 배치 / 정밀도 / seed | 32 / fp16 / 42 |

**무엇으로 학습했나 (X와 Y)**

| | ② 문서 재정렬 (`05`) | ④ hop 2 점수 (`08`) | ⑥ 문장 선택 (`06`) | ⑦ 검증 (`07`) |
|---|---|---|---|---|
| 배우는 질문 | 이 문서가 근거 문서인가? | 첫 문서를 보고 나서, 이 후보가 나머지 근거 문서인가? | 이 문장이 근거 문장인가? | 주장이 맞는가? |
| X: 텍스트 A | claim | `claim \| hop1 제목. hop1 본문` | claim | claim |
| X: 텍스트 B | `제목. 문서 본문` | `후보 제목. 후보 본문` | `제목. 문장` | 근거 문장 5개 이어 붙임 (제목 없음) |
| Y | 1 = 근거 문서 / 0 | 1 = 나머지 근거 문서 / 0 | 1 = 근거 문장 / 0 | 1 = SUPPORTED / 0 = NOT_SUPPORTED |
| Y의 출처 | `supporting_facts`의 제목 | `supporting_facts`의 제목 | `supporting_facts`의 (제목, 번호) | `label` |
| 최대 길이 | 256 | 256 | 128 | 384 |

**학습 데이터를 어떻게 만들었나**

| | ② 문서 재정렬 | ④ hop 2 점수 | ⑥ 문장 선택 | ⑦ 검증 |
|---|---|---|---|---|
| claim 하나에서 만드는 예시 | TF-IDF 후보 문서 20개 | 정답 문서 2개를 번갈아 hop 1로 × (양성 1 + 음성 7) = 16개 | 문서 5개의 모든 문장 (약 20개) | 1개 |
| 양성 (Y=1) | 정답 문서 2개 | 나머지 정답 문서 1개 | 정답 문장 2~4개 | SUPPORTED claim |
| 음성 (Y=0) | 정답이 아닌 TF-IDF 후보 | hop 2 후보 중 무작위 7개 | 나머지 문장 | NOT_SUPPORTED claim |
| 정답을 일부러 넣었나 | ✅ TF-IDF가 놓쳐도 정답 문서를 후보에 넣음 | ✅ hop 1 자리에 정답 문서 (teacher forcing) | ✅ 정답 문서를 5개 안에 넣음 | ❌ 06이 실제로 고른 문장 사용 (원본 HoVer 방식) |
| 전체 예시 수 | 약 16만 쌍 | 약 13만 쌍 | 약 16만 쌍 | 8,166개 |
| 양성 비율 | 약 10% | 12.5% | 약 10% | 72% |

검색 모델(②④⑥)은 앞 단계가 정답을 놓친 claim에서도 양성 예시를 봐야 배우므로 정답을 넣는다. 검증 모델은 실제로 받을 입력(잡음 섞인 근거)과 같은 형태로 배워야 하므로 정답을 넣지 않는다.

**어떻게 학습했나**

| | ② 문서 재정렬 | ④ hop 2 점수 | ⑥ 문장 선택 | ⑦ 검증 |
|---|---|---|---|---|
| epoch | 1 | 1 | 1 | 3 |
| 클래스 가중치 | ❌ | ❌ | ❌ | ✅ (NOT 1.77 / SUP 0.70) |
| 학습 중 평가 / 최종 모델 | 없음 / 마지막 시점 | 없음 / 마지막 시점 | 없음 / 마지막 시점 | epoch마다 val(검색된 근거) / val macro-F1 최고 epoch |
| "못 배운" 모델의 손실 | 약 0.33 | 약 0.38 | 약 0.33 | 0.693 (ln 2) |

| 차이 | 이유 |
|---|---|
| epoch 1 vs 3 | 검색 모델은 예시가 13~16만 개라 한 바퀴로 충분하다. 검증 모델은 8천 개뿐이라 여러 번 봐야 한다 |
| 클래스 가중치 | 검색 모델은 확률의 **순서**만 쓴다. 검증 모델은 확률로 **라벨을 정하고**, train(72:28)과 test(46:54)의 분포가 반대라 보정이 필요하다 |
| val로 모델 선택 | 검증 모델은 최종 점수에 직결되고 과적합 위험이 있다. 검색 모델은 1 epoch이라 고를 시점이 하나뿐이다 |

**결과를 어떻게 쓰고 평가하나**

| | ② 문서 재정렬 | ④ hop 2 점수 | ⑥ 문장 선택 | ⑦ 검증 |
|---|---|---|---|---|
| 추론 때 claim당 호출 | 20번 | 약 200번 | 약 20번 | 1번 |
| 출력 사용 | 점수 순 → 상위 2개가 hop 1 | P(hop 1) × P(hop 2) → 문서 순위 | 점수 순 → 상위 5문장 | 큰 확률 쪽 = Y |
| 평가 지표 | 문서 recall@k | 문서 recall@k | all_gold@k | accuracy, macro-F1, HoVer score |
| test 결과 | recall@5 56.7% | recall@5 83.6% (hop 1 → hop 2) | all_gold@5 46.3% (베이스라인) | macro-F1 0.736 (베이스라인) |

**요약**: 같은 `roberta-base`에서 출발해서, 검색 모델 세 개(②④⑥)는 "관련 있나?"를 **순위용으로** 대량의 쌍(13~16만)으로 1 epoch 학습했다. 검증 모델(⑦)은 "맞나?"를 **라벨용으로** 적은 claim(8천)으로 3 epoch 학습하고, 클래스 가중치와 val 선택을 더했다.

| `04_oracle` | 2 | 상한선: 정답 근거로 판정 | - |
| `05_doc_retrieval` | 3 | TF-IDF 후보 재정렬 | `hover2_*_docret.jsonl` |
| `08_multihop_retrieval` | 3-B | hop 1 → hop 2 검색 | `hover2_*_docret_mh.jsonl` |
| `06_sent_retrieval` | 4 | 문장 선택 (`TAG`로 3단계/3-B 결과 선택) | `hover2_*_sentret{TAG}.jsonl` |

`TAG = ''`이면 베이스라인, `TAG = '_mh'`이면 multi-hop 결과 파일을 읽고 쓴다. 둘은 서로 덮어쓰지 않는다.

### 3.3 세 모델의 공통 구조

세 모델 모두 **roberta-base + 출력 2개짜리 분류층**이다. 다른 것은 무엇을 쌍으로 넣고 무엇을 정답으로 주는지뿐이다.

| 모델 | 입력 쌍 | 맞히는 것 | 정답의 출처 |
|---|---|---|---|
| 문서 재정렬 | (claim, 제목. 문서 본문) | 이 문서가 근거 문서인가 | `supporting_facts`의 제목 |
| hop 2 점수 (3-B) | (claim \| hop 1 문서, 후보 문서) | 이 후보가 나머지 근거 문서인가 | `supporting_facts`의 제목 |
| 문장 선택 | (claim, 제목. 문장) | 이 문장이 근거 문장인가 | `supporting_facts`의 (제목, 번호) |
| 주장 검증 | (claim, 문장 k개 이어 붙임) | 주장이 맞는가 | `label` |

- val 점수가 test 점수를 잘 예측하지 못한다 → val은 모델 고르기에만 쓰고, 결론은 test로 낸다

### 4.5 정답 근거 문장 꺼내기

위키 DB의 `text`는 **문장 구분 없이 한 덩어리**다. 그런데 정답은 "몇 번 문장"으로 주어진다. 그래서 HoVer 저자들과 **똑같은 방식으로** 문장을 나눠야 번호가 맞는다.

- **도구**: Stanford CoreNLP의 `tokenize`, `ssplit`(문장 분리). 원본 HoVer 코드와 같다.
- **CoreNLP란**: Stanford에서 만든 Java 기반 영어 자연어 처리 도구 모음. 우리는 문장 분리 기능만 쓴다. 학습 모델이 아니라 **규칙 기반**이다(마침표 + 공백 + 대문자 → 문장 끝, 단 `Mr.`, `P. S.` 같은 약어는 예외).
- **왜 nltk/spaCy가 아닌가**: 약어나 괄호 처리 규칙이 조금씩 달라서 번호가 하나씩 밀릴 수 있다. 그러면 모델이 엉뚱한 문장을 정답으로 배우는데, **오류 메시지 없이 조용히** 성능만 떨어진다.
- **검증 1 (범위 확인)**: 정답 근거를 꺼내지 못한 claim이 train 19/8,166, val 3/886, test 2/1,126 (0.2~0.3%). 단, 이 확인은 번호가 범위를 **벗어난** 경우만 잡고, 범위 안에서 문장이 밀린 경우는 못 잡는다.
- **검증 2 (내용 대조)**: HotpotQA 데이터에는 문서가 이미 문장 단위로 나뉘어 있다(HoVer 번호의 출처). test 정답 문서 중 HotpotQA dev에도 있는 996개를 우리 CoreNLP 결과와 한 문장씩 비교했다.

  | 비교 | 결과 |
  |---|---|
  | 문서의 모든 문장이 완전히 일치 | 969 / 996 (97.3%) |
  | 정답 (제목, 번호) 1,222개가 같은 문장을 가리킴 | 1,206 (98.7%) |
  | 따옴표가 앞뒤 어느 문장에 붙는지만 다름 | 7 (0.6%) |
  | 실제로 다른 문장을 가리킴 | **9 (0.7%)** |

  어긋난 경우의 대부분은 HotpotQA 쪽이 `"Shrek 2"`의 숫자 뒤에서 문장을 잘못 끊은 것 같은 경우다. **정답 근거의 약 99%를 정확한 문장으로 쓰고 있다.**

### 4.6 유니코드 정규화 (NFC / NFD)

같은 글자도 컴퓨터에는 두 가지 방식으로 저장될 수 있다.

| 방식 | `é`의 저장 | 설명 |
|---|---|---|
| NFC (조합형) | `é` (1글자) | 일반적인 텍스트 |
| NFD (분해형) | `e` + `́` (2글자) | 위키 DB, TF-IDF 결과가 이 방식 |

화면에는 똑같이 `José Echegaray`로 보이지만 문자열 비교(`==`)에서는 **다른 값**이다. 정답 제목은 NFC, 위키 DB와 TF-IDF 제목은 NFD여서 같은 문서를 다른 문서로 셌다. 모든 제목을 비교 전에 NFC로 통일하도록 고쳤다([10장](#10-진행-중-발견한-문제와-교훈)). DB를 조회할 때는 DB 형식인 NFD로 바꿔서 찾는다.

## 5. 기초 이론

### 5.1 Transformer와 RoBERTa

**Transformer**는 문장의 모든 단어가 서로를 동시에 참고(self-attention)하면서 각 단어의 의미 벡터를 만드는 신경망 구조다. 앞뒤 문맥을 함께 보기 때문에 "bank"가 은행인지 강둑인지 문맥으로 구분할 수 있다.

**BERT / RoBERTa**는 Transformer 인코더를 대량의 텍스트로 미리 학습(pre-training)한 모델이다.
- **사전학습 과제**: 문장의 단어 일부를 가리고(mask) 맞히기. 이 과정에서 언어 지식을 익힌다.
- **RoBERTa**는 BERT와 구조가 같고 학습 방법을 개선한 버전이다(더 많은 데이터, 더 오래 학습, 다음 문장 예측 과제 제거).
- **roberta-base**: 12층, 은닉 차원 768, 파라미터 약 1.25억 개.

### 5.2 Fine-tuning (미세 조정)

사전학습된 모델(몸통)에 우리 작업용 출력층(머리)을 붙이고, 우리 데이터로 **전체를 조금 더 학습**하는 것이다.

```
입력 토큰
   │
[몸통] RoBERTa 인코더 12층   ← 사전학습 가중치를 그대로 가져옴
   │
   ├─ [머리 A] lm_head      ← 사전학습용 "가려진 단어 맞히기" 층 → 버림 (UNEXPECTED)
   └─ [머리 B] classifier   ← 우리 작업용 2-클래스 분류층 → 새로 만듦 (MISSING)
```

모델을 불러올 때 나오는 `LOAD REPORT`의 `UNEXPECTED lm_head.*`, `MISSING classifier.*`는 위 그림대로라서 **정상**이다.

**제로샷과의 차이**: 제로샷은 학습 없이 기존 모델을 그대로 쓰는 것이다. 우리는 모든 단계에서 train 데이터로 fine-tuning했다.

### 5.3 손실 함수: Cross-Entropy와 클래스 가중치

**분류 모델의 출력**: 클래스마다 점수(logit) $z_0, z_1$를 내고, softmax로 확률로 바꾼다.

$$P(y = i) = \frac{e^{z_i}}{e^{z_0} + e^{z_1}}$$

**Cross-entropy 손실**: 정답 클래스에 준 확률이 낮을수록 큰 벌점.

$$\mathcal{L} = -\log P(y = \text{정답})$$

| 정답에 준 확률 | 손실 |
|---|---|
| 0.99 | 0.01 (거의 맞음) |
| 0.5 | 0.693 (반반으로 찍음) |
| 0.01 | 4.6 (확신하며 틀림) |

**클래스 가중치**: 적은 클래스를 틀렸을 때 벌점을 더 준다.

$$w_c = \frac{N}{K \cdot N_c} \qquad \mathcal{L} = -\,w_{\text{정답}} \log P(y = \text{정답})$$

($N$ = 전체 개수, $K$ = 클래스 수 2, $N_c$ = 클래스 $c$의 개수)

train에 넣으면 NOT_SUPPORTED $\approx$ 1.77, SUPPORTED $\approx$ 0.70이다. NOT_SUPPORTED 한 건을 틀리면 약 2.5배의 벌점을 받는다. 개수 × 가중치가 두 클래스에서 같아지므로, 학습 중에는 **50:50 데이터처럼** 작동한다. 데이터를 복제하거나 버리지 않고 계산 방식만 바꾼다는 점이 오버/언더샘플링과 다르다.

- **검증 모델(1·2·5단계)**: 클래스 가중치 사용. 라벨 판정 자체가 목표라 기울어지면 안 된다.
- **검색 모델(3·4단계)**: 사용하지 않음. 확률의 **순서**만 쓰므로, 가중치가 바꾸는 확률의 절대값은 결과에 거의 영향이 없다.

### 5.4 손실 값으로 학습 상태 읽기

"아무것도 배우지 않은 모델"의 손실을 알면 학습이 되고 있는지 판단할 수 있다.

| 상황 | 아무것도 못 배운 모델의 손실 | 의미 |
|---|---|---|
| 클래스 가중치 사용 (검증기) | $\ln 2 \approx$ **0.693** | 가중치 때문에 50:50처럼 작동 → 항상 0.5를 주는 상태 |
| 양성 10%, 가중치 없음 (문서/문장 검색) | $-(0.1\ln 0.1 + 0.9\ln 0.9) \approx$ **0.33** | 내용은 안 보고 "10%가 정답"이라는 비율만 배운 상태 |
| 양성 1/8, 가중치 없음 (hop 2) | 약 **0.38** | 같은 원리 |

**손실이 이 값에 계속 머물면 학습 실패**다. 실제로 5단계 첫 실행에서 손실이 0.693에 고정된 채 모든 claim에 같은 답을 내는 일이 있었다([10장](#10-진행-중-발견한-문제와-교훈)).

### 5.5 학습 설정 용어

| 용어 | 뜻 | 이 프로젝트의 값 |
|---|---|---|
| **배치 (batch)** | 한 번에 묶어 처리하는 예시 수 | 32 |
| **스텝 (step)** | 배치 하나로 가중치를 한 번 업데이트 | 전체 = ⌈예시 수 / 32⌉ × epoch |
| **epoch** | train 전체를 한 바퀴 도는 것 | 검증기 3, 검색 모델 1 |
| **learning rate** | 한 번 업데이트할 때 움직이는 크기 | 2e-5 |
| **warmup** | 처음 일정 비율의 스텝 동안 learning rate를 0에서 서서히 올림. 초반 불안정 방지 | 10% (`warmup_steps=0.1`) |
| **weight decay** | 가중치가 너무 커지지 않게 하는 규제 | 0.01 |
| **fp16** | 16비트 실수로 계산해 GPU 속도와 메모리 절약 | 사용 |
| **seed** | 무작위 요소(초기화, 데이터 순서)를 고정하는 값 | 42 |
| **logging_steps** | 몇 스텝마다 손실을 평균 내서 출력하는지 | 50~200 |
| **load_best_model_at_end** | epoch마다 val로 평가해서 가장 좋은 시점의 모델을 최종으로 씀 | 검증기에 사용 (기준: val macro-F1) |

### 5.6 토큰화와 문장 쌍 입력

**토큰화**: 문장을 모델이 아는 조각(토큰)으로 자르는 것. RoBERTa는 BPE 방식이라 흔한 단어는 통째로, 드문 단어는 여러 조각으로 나눈다.

**문장 쌍 입력**: 두 텍스트를 특수 토큰으로 이어 붙여 한 번에 넣는다.

```
<s> claim </s></s> 근거 텍스트 </s>
```

- `<s>`: 시작 토큰. 이 위치의 출력 벡터가 분류층으로 들어간다(BERT의 `[CLS]`).
- 모델 안에서 claim의 단어와 근거의 단어가 서로를 직접 참고하므로, "Krøyer"와 "Krøyer"가 맞는지, "1668"과 "1670"이 다른지를 비교할 수 있다.

**최대 길이와 자르기 (truncation)**: 입력이 `max_length`를 넘으면 자른다.
- `only_second`: 두 번째(근거)만 자름. claim이 너무 길면 자를 곳이 없어 **오류**가 난다.
- `True` (`longest_first`): 둘 중 긴 쪽부터 자름. 오류가 나지 않아서 4단계부터 이 방식을 썼다.

| 단계 | max_length | 이유 |
|---|---|---|
| 1 claim-only | 128 | claim만 |
| 2 oracle | 256 | claim + 정답 문장 2~4개 |
| 3 문서 재정렬, 3-B hop 2 | 256 | 문서 도입부 문단 |
| 4 문장 선택 | 128 | claim + 문장 하나 |
| 5 검증 | 384 | claim + 문장 최대 10개 |

### 5.7 검색(Retrieval) 이론

#### 희소 검색 (Sparse Retrieval): TF-IDF

문서와 질의를 **단어 빈도 벡터**로 표현하고 겹치는 정도로 점수를 매긴다. 대부분의 값이 0이라 "희소(sparse)"라고 부른다.

$$\text{tf-idf}(t, d) = \text{tf}(t, d) \times \log\frac{N}{\text{df}(t)}$$

- $\text{tf}(t, d)$: 문서 $d$에 단어 $t$가 나온 횟수 → 많이 나올수록 중요
- $\text{df}(t)$: 단어 $t$가 나온 문서 수, $N$: 전체 문서 수 → 여러 문서에 흔하게 나오는 단어("the", "was")는 가중치가 낮고, 드문 단어("Krøyer", "Skagen")는 높다
- 질의와 문서의 TF-IDF 벡터 유사도(코사인 등)로 순위를 매긴다.
- HoVer 저자들은 **DrQA**의 구현을 썼다. 단어 하나(unigram)와 두 단어 묶음(bigram)을 해싱해서 TF-IDF를 계산한다.

| 장점 | 단점 |
|---|---|
| 학습이 필요 없음, 520만 문서도 빠르게 검색 | **단어가 겹쳐야만** 찾음. 뜻이 같아도 단어가 다르면 못 찾음 |
| 결과를 해석하기 쉬움 | **claim에 이름이 나오지 않는 문서를 못 찾음** (bridge 문제) |

**BM25**는 TF-IDF를 개선한 희소 검색 함수로, 단어 빈도의 효과가 일정 수준에서 포화되게 하고 문서 길이를 보정한다. 현재 검색 시스템의 표준 기준선이다.

#### 밀집 검색 (Dense Retrieval): 바이 인코더

질의와 문서를 **각각** 신경망으로 벡터 하나씩으로 만들고, 벡터 내적으로 유사도를 잰다(DPR 등).

```
claim ──▶ 인코더 ──▶ 벡터 q ┐
                              ├─ q · d = 유사도
문서  ──▶ 인코더 ──▶ 벡터 d ┘   (문서 벡터는 미리 계산해 둠)
```

- 장점: 단어가 달라도 뜻이 비슷하면 찾는다. 문서 벡터를 미리 계산해 두면 검색이 빠르다.
- 단점: 520만 문서를 모두 벡터로 만드는 데 GPU 시간이 많이 든다. 학습이 필요하다.

#### 크로스 인코더 (Cross-Encoder): 재정렬

질의와 문서를 **이어 붙여 한 번에** 넣고 관련도 점수 하나를 받는다. 이 프로젝트의 3·4단계 모델이 이 방식이다.

```
<s> claim </s></s> 문서 </s> ──▶ roberta ──▶ P(관련 있음)
```

- 장점: 두 텍스트의 단어가 모델 안에서 직접 비교되므로 **가장 정확**하다.
- 단점: 후보마다 모델을 한 번씩 돌려야 해서 **느리다**. 520만 문서 전체에는 쓸 수 없다.

#### Retrieve-then-Rerank (2단 검색)

빠르지만 거친 방법으로 후보를 줄이고, 느리지만 정확한 방법으로 순서를 매긴다. 검색 시스템의 표준 구성이다.

```
520만 문서 ──[TF-IDF, 빠름]──▶ 후보 20개 ──[크로스 인코더, 정확]──▶ top-5
```

**중요한 성질: 재정렬은 순서만 바꾼다.** 1차 후보에 정답이 없으면 재정렬로 되살릴 수 없다. 그래서 1차 후보의 recall이 전체 검색의 **천장**이 된다.

## 6. 지표 이론: 무엇을 왜 쓰는가

### 6.1 Accuracy와 혼동행렬

**혼동행렬**: 실제 라벨과 예측 라벨의 조합별 개수. 베이스라인(test)의 예:

|  | 예측 NOT_SUPPORTED | 예측 SUPPORTED |
|---|---|---|
| **실제 NOT_SUPPORTED** | 444 (TN) | 161 (FP) |
| **실제 SUPPORTED** | 135 (FN) | 386 (TP) |

(SUPPORTED를 양성으로 볼 때 TP = 참 양성, FP = 거짓 양성, FN = 거짓 음성, TN = 참 음성)

**Accuracy** = 맞힌 비율

$$\text{Accuracy} = \frac{TP + TN}{\text{전체}} = \frac{386 + 444}{1126} = 0.737$$

**약점**: 클래스가 한쪽으로 몰려 있으면 착시가 생긴다. val에서 "항상 SUPPORTED"라고만 답해도 accuracy가 0.718이다. 아무것도 배우지 않았는데 높아 보인다.

### 6.2 Precision, Recall, F1, Macro-F1

클래스 하나(예: NOT_SUPPORTED)에 대해:

$$\text{Precision} = \frac{\text{맞게 그 클래스라고 한 수}}{\text{그 클래스라고 예측한 수}} \qquad \text{Recall} = \frac{\text{맞게 그 클래스라고 한 수}}{\text{실제 그 클래스의 수}}$$

- **Precision(정밀도)**: "NOT이라고 했을 때 얼마나 믿을 수 있나"
- **Recall(재현율)**: "실제 NOT을 얼마나 놓치지 않고 잡았나"
- 둘은 보통 반비례한다. 다 NOT이라고 하면 recall은 1이지만 precision은 낮다.

**F1** = 둘의 조화 평균. 한쪽만 높으면 F1이 낮다.

$$F_1 = \frac{2 \cdot P \cdot R}{P + R}$$

**Macro-F1** = 클래스별 F1의 **단순 평균**.

$$\text{Macro-F1} = \frac{F_1^{\text{SUPPORTED}} + F_1^{\text{NOT\_SUPPORTED}}}{2}$$

클래스 크기와 상관없이 두 클래스를 **똑같이** 중요하게 본다. 한 클래스를 완전히 무시하면 그 클래스의 F1이 0이 되어 macro-F1이 크게 떨어진다. "항상 SUPPORTED"의 test macro-F1이 0.316밖에 안 되는 이유다.

**왜 썼나**: train(SUPPORTED 72%)과 test(46%)의 분포가 반대라서 accuracy만으로는 비교가 왜곡된다. 이 프로젝트의 **검증 단계 주 지표**다.

### 6.3 Recall@k (문서 검색)

**정의**: 정답 문서가 **모두** 상위 k개 안에 들어온 claim의 비율.

$$\text{Recall@}k = \frac{1}{|Q|} \sum_{q \in Q} \mathbb{1}\left[\,\text{Gold}(q) \subseteq \text{Top}_k(q)\,\right]$$

```
정답 문서: {The Assignation, John Dryden}
top-5: [The Assignation, Poet Laureate, John Dryden, ...]  → 1점 (둘 다 있음)
top-5: [The Assignation, Poet Laureate, Restoration, ...]  → 0점 (하나 빠짐)
```

**왜 accuracy나 precision이 아닌가**
- 후보 20개 중 정답은 2개뿐이라, "전부 정답 아님"이라고만 해도 쌍 단위 accuracy가 90%다. 의미가 없다.
- **엉뚱한 문서가 섞이는 건(precision↓) 다음 단계(문장 선택)에서 걸러진다.**
- **정답 문서를 놓치는 건(recall↓) 되돌릴 수 없다.** 뒤 단계에 아예 전달되지 않는다.
- 2-hop 검증에는 두 문서가 모두 필요하므로 "모두"를 기준으로 한다.

**보조 지표: 문서 단위 recall** = 찾은 정답 문서 수 / 전체 정답 문서 수. "모두" recall과의 차이가 크면 **하나는 찾고 하나를 놓치는** 경우가 많다는 뜻이다.

원본 HoVer는 recall@5, 8, 10을 보고한다. 우리는 2, 5, (8), 10, 20을 봤다.

### 6.4 문장 선택 지표

| 지표 | 계산 | 의미 |
|---|---|---|
| **all_gold@k** | 정답 문장이 top-k에 **모두** 있는 claim 비율 | 주 지표. HoVer score와 직결 |
| recall@k | claim별 (찾은 정답 문장 / 전체 정답 문장)의 평균 | 부분적으로라도 얼마나 찾았나 |
| precision@k | claim별 (top-k 중 정답 문장 / k)의 평균 | 검증기에 들어가는 잡음의 양 |
| 천장 | 문서 recall@5 | 문서를 놓치면 그 안의 문장도 고를 수 없음 |

k를 늘리면 recall은 오르고 precision은 떨어진다. 이 균형을 val에서 정한다.

### 6.5 HoVer Score

**정의**: 라벨이 맞고, **동시에** 정답 근거 문장이 예측한 근거(top-k) 안에 모두 있을 때만 1점.

$$\text{HoVer score} = \frac{1}{|Q|}\sum_{q} \mathbb{1}[\hat{y}_q = y_q] \cdot \mathbb{1}[\text{GoldSents}(q) \subseteq \text{PredSents}_k(q)]$$

**왜 필요한가**: claim-only 모델이 62%를 맞혔듯이, 근거 없이 표현만 보고 우연히 라벨을 맞힐 수 있다. HoVer score는 **"올바른 근거를 보고 맞혔는가"**를 잰다. HoVer 공식 지표다.

- 이 프로젝트에서는 k=5로 고정해서 보고한다. 문장을 많이 넘길수록 정답이 그 안에 들어갈 확률이 저절로 올라가서, k가 다르면 공정한 비교가 안 된다.
- 항상 accuracy보다 낮고, 문장 선택의 all_gold@k보다도 낮다.

### 6.6 EM / F1 (원본 HoVer 문서·문장 검색 지표)

원본 코드에는 모델이 "정답"이라고 **고른 집합**과 정답 집합을 비교하는 지표도 있다.
- **EM (Exact Match)**: 두 집합이 정확히 같으면 1
- **F1**: 두 집합의 precision과 recall의 조화 평균

확률 기준값으로 문서/문장을 골라낼 때 쓰는 지표다. 우리는 top-k를 그대로 넘기므로 recall@k와 all_gold@k를 썼다.

## 7. 실험 설계: 하한선과 상한선

### 7.1 왜 두 기준이 필요한가

최종 점수 0.736 하나만으로는 좋은지 나쁜지 알 수 없다. 그래서 같은 모델 구조로 **비교 기준 두 개**를 먼저 만들었다.

| 기준 | 방법 | 재는 것 |
|---|---|---|
| **하한선 (claim-only)** | 근거 없이 claim만 넣음 | 데이터 편향만으로 맞힐 수 있는 수준 |
| **상한선 (oracle)** | 정답 근거를 직접 넣음 | 검색이 완벽할 때 검증기의 최대 성능 |

```
0.316        0.620                  0.736        0.800
  |------------|----------------------|------------|
다수 클래스   하한선                 베이스라인    상한선
             └── 근거의 효과 +0.116 ──┘└ 검색 손실 ┘
                                          -0.064
```

- **베이스라인 − 하한선** = 검색한 근거가 실제로 준 도움
- **상한선 − 베이스라인** = 검색이 불완전해서 잃은 성능
- 간격 회복률 = (0.736 − 0.620) / (0.800 − 0.620) = **64%**

### 7.2 다음에 무엇을 고칠지 정하는 법

| 상황 | 해석 | 고칠 곳 |
|---|---|---|
| 최종 점수 ≈ 상한선 | 검색은 충분히 잘 됨 | 검증기 |
| 최종 점수 ≈ 하한선 | 검색이 근거를 거의 못 찾음 | 검색 |
| 중간 | 둘 다 | 검색 recall을 보고 판단 |

현재는 근거를 다 찾은 claim의 점수(0.783)가 상한선에 가깝고, 놓친 claim이 많으므로 **검색이 우선**이다.

### 7.3 val과 test 사용 원칙

- **val**: 모델 고르기(epoch), 설정 고르기(k, 클래스 가중치). 여러 번 봐도 된다.
- **test**: 마지막에 보고만 한다. test를 보고 설정을 바꾸면 test에 맞춘 설정이 되어 점수가 부풀려진다.
- 예외로 기록할 점: multi-hop 설계 분석(9.3절)은 test claim으로 했다. 그래서 08 노트북 3번 셀에서 **val로 같은 수치를 다시 확인**한다.

### 1단계: 하한선, claim-only (`03_claim_only`)

| 항목 | 내용 |
|---|---|
| 입력 → 출력 | `<s> claim </s>` → SUPPORTED / NOT_SUPPORTED |
| 학습 | roberta-base, 3 epoch, val macro-F1로 최고 epoch 선택 |
| 실험 | 클래스 가중치 끄기 / 켜기 |

| test | acc | macro-F1 | NOT 재현율 | SUP 재현율 |
|---|---|---|---|---|
| 항상 SUPPORTED | 0.463 | 0.316 | 0% | 100% |

- 가중치 없음의 accuracy 0.520은 "항상 NOT_SUPPORTED"(0.537)보다 낮다. accuracy만 보면 위험한 이유.

### 2단계: 상한선, oracle (`04_oracle`)

| 항목 | 내용 |
|---|---|
| 입력 → 출력 | `<s> claim </s></s> 정답 근거 문장들 </s>` → 라벨 |
| 학습 | 1단계와 같음 + 클래스 가중치 |

| test | acc | macro-F1 | NOT 재현율 | SUP 재현율 |
|---|---|---|---|---|
| **oracle** | **0.800** | **0.800** | 72% | 89% |

(val macro-F1 0.839)

**해석**
- 근거를 넣으니 +18%p. 모델이 claim과 근거를 실제로 대조한다.
- 오류 225건 중 170건이 **"틀린 주장을 맞다고 판정"**이다. HoVer는 단어 한두 개만 바꿔 라벨을 뒤집은 claim이 많다. 근거와 거의 겹치는 작은 차이를 놓치는 것으로 추정한다.

### 3단계: 문서 검색 (`05_doc_retrieval`)

| 항목 | 내용 |
|---|---|
| 1차 | TF-IDF top-100 (저자 제공) |
| 재정렬 입력 | `<s> claim </s></s> 제목. 문서 본문 </s>` → P(정답 문서) |
| 후보 수 | claim당 20개 (원본 HoVer와 같음) |
| 학습 데이터 | claim당 20쌍, 약 16만 쌍. **학습 때는 정답 문서를 항상 포함**(TF-IDF가 놓친 claim도 양성 예시를 갖게, 원본 방식) |
| 학습 | 1 epoch, 클래스 가중치 없음 |

| test (두 정답 문서 모두) | top-2 | top-5 | top-10 | top-20 |
|---|---|---|---|---|
| TF-IDF | 23.3% | 37.9% | 48.9% | 58.0% |
| **재정렬** | **50.4%** | **55.8%** | 57.7% | 58.0% |

(NFC 정규화 버그 때문에 위 숫자는 약 2%p 낮게 잡혀 있다. 실제 TF-IDF top-20은 60.2%)

**해석**
- 재정렬은 거의 천장까지 갔다. 후보 안에 정답이 있으면 96%를 top-5로 올린다.
- **병목은 1차 후보다.** 약 40%의 claim은 후보 20개 안에 정답 문서가 아예 없다.
- 문서 단위로 세면 top-20 recall이 76%인데 "모두"는 58%. **하나는 찾고 하나를 놓치는 경우가 많다** → multi-hop 동기.

### 4단계: 문장 선택 (`06_sent_retrieval`)

| 항목 | 내용 |
|---|---|
| 후보 | 3단계 top-5 문서의 모든 문장 (CoreNLP로 분리, 원본과 같은 번호) |
| 입력 | `<s> claim </s></s> 제목. 문장 </s>`. 제목을 붙이는 이유: "He was a Danish painter"만으로는 He가 누구인지 모른다 |
| 학습 데이터 | 약 16만 쌍, 양성 약 10%. 학습 때는 정답 문서 포함 |
| 학습 | 1 epoch |

| test | top-2 | top-3 | top-4 | **top-5** | 천장 |
|---|---|---|---|---|---|
| all_gold | 25.9% | 36.7% | 43.0% | **46.3%** | 55.8% |
| recall | 57.9% | 65.1% | 68.8% | 70.5% | |
| precision | 67.1% | 51.4% | 41.3% | 34.0% | |

**해석**
- 천장 대비 83%. 문서만 찾으면 문장도 대부분 고른다.
- top-2가 낮은 건 구조적 이유도 있다. 32%의 claim은 정답 문장이 3개 이상이다.
- val에서 k=5를 골랐다(4→5에서도 아직 오름, 정답 문장 5개 초과는 1.4%뿐).

### 5단계: End-to-end 검증 (`07_end_to_end`)

| 항목 | 내용 |

## 9. Multi-hop 검색 상세

### 9.1 Single-shot 검색의 한계

베이스라인의 검색은 **claim 하나로 한 번** 검색한다. 각 후보 문서는 claim과의 관련도만으로 **서로 독립적으로** 점수를 받는다.

```
claim ─┬─▶ (claim, 문서 A) → 0.97
       ├─▶ (claim, 문서 B) → 0.89      ← 다른 문서의 내용은 전혀 쓰지 않음
       └─▶ (claim, 문서 C) → 0.21
```

"문서 A를 읽었으니 다음엔 무엇을 찾자"는 과정이 없다. 그래서:
- **Comparison claim**: 두 이름이 claim에 다 있으므로 대체로 괜찮다.
- **Bridge claim**: 두 번째 문서 이름이 claim에 없어서, 첫 문서를 읽기 전에는 찾을 수 없다.

### 9.2 Multi-hop 검색의 원리 (Iterative Retrieval)

**찾은 문서를 다음 검색의 단서로 쓴다.**

```
hop 1:  검색어 = claim
        → "The Assignation" 문서 ("...a play by John Dryden...")

hop 2:  검색어 = claim + "The Assignation" 문서 내용
        → 이제 "John Dryden"이 검색어에 있으므로 John Dryden 문서를 찾을 수 있음
```

이론적으로는 문서 쌍 $(a, c)$의 확률을 두 단계로 나눈다.

$$P(a, c \mid q) = P(a \mid q) \cdot P(c \mid q, a)$$

- $P(a \mid q)$: claim $q$로 첫 문서 $a$를 찾을 확률 (hop 1)
- $P(c \mid q, a)$: claim과 첫 문서를 **함께 보고** 두 번째 문서 $c$를 찾을 확률 (hop 2)

#### 설계할 때 정해야 하는 것

| 결정 | 선택지 | 설명 |
|---|---|---|
| **다음 검색어를 어떻게 만드나** (query reformulation) | 첫 문서 전체를 붙이기 / 근거 문장만 요약해 붙이기 | 붙일수록 정보가 많지만 잡음도 늘어남 |
| **몇 개를 들고 넘어가나** (beam search) | hop 1 상위 B개를 동시에 따라감 | B=1이면 hop 1에서 틀렸을 때 회복 불가. B가 크면 비용 증가 |
| **어디서 hop 2 후보를 찾나** | 전체 코퍼스 재검색 / 하이퍼링크 따라가기 | 재검색은 인덱스가 필요, 링크는 빠르지만 링크가 있어야 함 |
| **언제 멈추나** | hop 수 고정 / 모델이 "충분하다"고 판단 | 2-hop만 다루면 2번 고정이 가장 단순 |

#### 대표 연구

| 방법 | 핵심 아이디어 |
|---|---|
| **하이퍼링크 기반** (Asai et al., 2020, *Learning to Retrieve Reasoning Paths*) | 위키 문서의 링크를 따라 다음 문서 후보를 만들고, 경로(문서 순서)를 점수화 |
| **MDR** (Xiong et al., 2021, *Multi-Hop Dense Retrieval*) | 질의 + 첫 문서를 이어 붙여 다시 밀집 검색. beam search로 문서 쌍을 찾음 |
| **Baleen** (Khattab et al., 2021) | hop마다 찾은 근거를 짧게 요약(condense)해서 다음 검색어에 붙임. HoVer에서도 평가 |

실제 노트북은 TF-IDF보다 정확한 **재정렬 상위 문서**를 hop 1로 쓰므로 더 높아질 것으로 예상한다.

### 9.4 우리 설계

```
hop 1:       3단계 재정렬 top-B 문서 (B=2)                         a₁, a₂
               │
hop 2 후보:  claim에 언급된 위키 제목 ∪ aᵢ 본문에 언급된 위키 제목
               │
hop 2 점수:  roberta  <s> claim | aᵢ. aᵢ 본문 </s></s> c. c 본문 </s>  → P(c | claim, aᵢ)
               │
경로 점수:   P(aᵢ) × P(c | claim, aᵢ)
               │
최종 순위:   ① 최고 경로의 (aᵢ, c)를 맨 앞에
             ② 나머지는 hop 1 순위와 다음 경로들을 번갈아 채움 (최대 20개)
               ▼
4단계(06, TAG='_mh') → 5단계(07, TAG='_mh')
```

#### hop 2 후보 생성: "링크 따라가기"를 흉내 내기

우리 위키 DB는 **링크가 제거된 버전**(`wiki_wo_links`)이다. 그래서 본문에 등장하는 위키 제목을 직접 찾아 링크를 복원한다.

1. 위키의 모든 제목(약 480만 개 이름)으로 사전을 만든다. `Life Goes On (Fergie song)`처럼 괄호가 붙은 제목은 괄호를 뗀 `life goes on`으로도 찾을 수 있게 묶는다.
2. 본문(또는 claim)을 단어로 자르고, **대문자나 숫자로 시작하는** 1~8단어 구간을 사전과 대조한다.
3. 한 단어짜리 불용어("The", "It", 월 이름 등)와 2글자 이하는 제외한다.

| 필터 | 후보 수 (평균) | 놓친 문서 포함률 |
|---|---|---|
| 모든 구간 | 367 | 51.8% |
| **대문자 시작 구간만** | **134** | **51.6%** |

대문자 필터는 포함률을 거의 그대로 두면서 후보를 1/3로 줄인다. 위키 제목은 대부분 고유명사라서 그렇다.

#### hop 2 모델 학습 데이터

train claim마다 **정답 문서 하나를 hop 1로 가정**하고:
- 양성: 나머지 정답 문서 (후보에 없어도 넣는다. 3단계와 같은 이유)
- 음성: hop 2 후보 중 무작위 7개
- 정답 문서 두 개를 번갈아 hop 1로 쓴다 → claim당 16쌍, 약 13만 쌍, 양성 비율 1/8

학습 때 hop 1을 정답으로 주는 것은 **teacher forcing**과 같은 방식이다. 추론 때는 모델이 고른 hop 1을 쓴다.

#### 결과를 합치는 방식이 중요한 이유

처음에는 경로 점수 순서로만 20개를 채웠다. 그러면 **hop 1 순위 3~20위에 있던 정답 문서가 밀려난다.** 로컬 테스트에서 recall@20이 0.55 → 0.20으로 떨어지는 것을 보고 고쳤다. 지금은 최고 경로를 앞에 두고 hop 1 순위와 다음 경로를 번갈아 채워서, hop 1이 이미 잘 찾던 문서를 지킨다.

### 9.5 08 노트북 결과

두 정답 문서가 모두 top-k 안에 들어온 비율이다.

| | top-2 | top-5 | top-10 | top-20 |
|---|---|---|---|---|
| val hop 1만 (베이스라인) | 59.4% | 65.5% | 66.7% | 67.7% |
| **val hop 1 → hop 2** | **75.5%** | **86.3%** | **89.5%** | **90.5%** |
| test hop 1만 (베이스라인) | 50.8% | 56.7% | 59.7% | 60.2% |
| **test hop 1 → hop 2** | **71.1%** | **83.6%** | **87.5%** | **88.3%** |
| test 차이 | +20.3%p | **+26.9%p** | +27.8%p | +28.1%p |

**해석**
- **검색 천장을 넘었다.** 베이스라인은 TF-IDF 후보 20개 안에서 순서만 바꾸므로 60.2%가 한계였다. hop 2는 그 밖의 문서를 가져와 88.3%에 이른다. 정답 문서를 hop 1로 줬을 때의 상한(88.7%)에 거의 닿았다. 재정렬한 hop 1이 대부분 정답 문서를 맞힌다는 뜻이다.
- **recall@5가 가장 중요하다.** 4단계가 top-5 문서를 쓰므로 문장 선택의 천장이 56.7% → 83.6%로 오른다.
- **val에서도 같은 경향이다.** 설계 분석은 test로 했지만, val에서도 같은 폭으로 올라서 test에 맞춘 결과가 아니다.
- **버그 수정 확인.** "hop 1만" recall@20 60.2%는 로컬에서 NFC로 맞춰 계산한 값과 같다(이전 58.0%는 표기 버그).

**해석할 때 주의할 점**: 향상분에는 (1) **claim에 언급된 제목**을 후보로 넣은 효과(비교형 claim에서 TF-IDF가 놓친 문서. 엄밀히는 multi-hop보다 개체 연결에 가깝다)와 (2) **hop 1 본문에 언급된 제목**을 넣은 효과(진짜 bridge 연결)가 섞여 있다. 둘을 나누려면 후보를 한쪽만 쓰는 비교 실험(ablation)이 필요하다.

다음으로 `06`, `07`을 `TAG='_mh'`로 돌려 최종 점수를 비교한다.

| 비교 (test) | 베이스라인 | Multi-hop |
|---|---|---|
| 문서 recall@5 | 56.7% (NFC 기준) | **83.6%** |
| 문장 all_gold@5 | 46.3% | **70.8%** (천장 대비 85%, recall@5 85.2%, precision@5 40.6%) |
| accuracy | 0.737 | **0.763** |
| 검증 macro-F1 | 0.736 | **0.763** (+2.7%p) |
| HoVer score | 0.362 | **0.570** (+20.8%p) |
| 간격 회복률 (하한선 0.620 → 상한선 0.800) | 64% | **79%** |
| 근거를 다 찾은 claim | 521개 (macro-F1 0.783) | **797개** (macro-F1 0.804) |
| 근거를 놓친 claim | 605개 (macro-F1 0.694) | **329개** (macro-F1 0.654) |
| 같은 검증 모델에 정답 근거를 넣으면 | - | 0.785 |

**해석**
- **HoVer score가 1.6배**가 됐다. 근거를 다 찾은 claim이 521개 → 797개로 늘었기 때문이다.
- **macro-F1은 +2.7%p로 상대적으로 적게 올랐다.** 근거를 다 찾은 claim의 성능(0.804)이 이미 상한선(0.800)과 같고, 정답 근거를 넣어도 0.785다. 검색이 좋아질수록 라벨 정확도는 **검증 모델 자체의 천장(약 0.80)**에 막힌다.
- **병목이 검색에서 검증 모델로 바뀌었다.** 검색 실패 claim이 54% → 29%로 줄었고, 남은 오류는 근거를 찾고도 판정을 틀리는 경우의 비중이 커졌다. 틀린 267건 중 189건이 "틀린 주장을 맞다고 판정"(NOT_SUPPORTED 재현율 69%, SUPPORTED 85%)으로, oracle과 같은 패턴이다.

### 9.6 Multi-hop 설계의 한계

| 한계 | 영향 | 개선 방향 |
|---|---|---|
| 반대 방향 관계 (놓친 문서가 찾은 문서를 언급) | 한 문서만 찾은 claim의 약 20% | "이 제목을 언급하는 문서" 역색인 만들기 |
| 표기가 다른 언급 ("Dryden" ↔ "John Dryden") | 일부 놓침 | 성(姓)만으로도 찾기, 밀집 검색 |
| 둘 다 놓친 claim (72건) | hop 1부터 실패 | 1차 후보를 100개로 늘리기 (TF-IDF top-100 천장 74%) |
| 후보가 많음 (claim당 약 200개) | 추론 시간 | 후보 수 상한, 더 강한 필터 |
| hop 1 오류가 전파됨 | hop 1이 틀리면 hop 2도 틀림 | beam 크기 B 조절 |

### 9.7 3·4-hop으로 확장할 때

- **hop 수**: 2-hop은 2번 고정. 3·4-hop은 hop 1 → 2 → 3 …으로 반복한다. 같은 구조를 그대로 쓰되, 다음 검색어에 지금까지 찾은 문서들을 모두 붙인다.
- **hop 수를 모르는 문제**: 실제로는 claim이 몇 hop인지 모른다. 원본 HoVer는 hop을 구분하지 않고 섞어 학습했다. 선택지는 (1) 최대 hop 수로 고정하고 넉넉하게 검색, (2) 멈춤 판단 모델 추가.
- **추천 순서**: 2-hop에서 multi-hop 검색의 효과를 확인 → 같은 틀로 3·4-hop 확장. 2-hop에서 먼저 검증해야 점수 변화가 방법 때문인지 hop 증가 때문인지 구분할 수 있다.

| **CoreNLP 서버 시작 실패** | `CORENLP_HOME` 없음 / 포트 9000 타임아웃 / 9011 이미 사용 중 | stanza 설치 경로와 서버가 찾는 경로가 다름. Colab에서 9000번 포트 문제. 이전 서버가 남아 있음 | 설치 경로를 `CORENLP_HOME`에 지정, 9011 포트, `StartServer.TRY_START`(떠 있으면 재사용) |

| **진행 표에 중간 손실이 안 보임** | `logging_steps`를 줄여도 epoch 끝까지 손실이 안 나옴 | 노트북 진행 표는 epoch 평가 모드에서 중간 손실을 표시하지 않음 | `disable_tqdm=True`로 텍스트 로그 출력 |
| **모델 체크포인트 소실** | oracle 검증기를 5단계에서 재사용 못 함 | Colab 런타임이 끊기면 `/content`가 사라짐 | 결과(예측)는 Drive에 저장. 모델이 필요하면 Drive에 저장 |
| **토큰 자르기 오류** | `Sequence to truncate too short` | `only_second`는 claim이 길면 자를 곳이 없음 | `truncation=True` (긴 쪽부터 자름) |

**교훈**: 오류 없이 조용히 틀리는 문제(문장 번호 어긋남, 유니코드 표기)가 가장 위험하다. "천장보다 높은 값이 나오면 안 된다", "정답 근거를 넣으면 점수가 올라야 한다" 같은 **상식 검사**와 단계별 숫자 대조가 이런 문제를 잡아냈다.

## 11. 한계와 다음 단계

### 현재 한계

- **seed 하나, 실행 한 번**: 몇 %p는 실행마다 달라질 수 있다. 결론(검색이 병목)은 차이가 커서 바뀌지 않지만, 작은 차이를 비교하려면 여러 seed 평균이 필요하다.
- **NFC 버그를 고친 뒤 베이스라인 재실행 전**: 검색 지표가 약 2%p 낮게 잡혀 있다.
- **데이터 편향**: claim만으로 62%. 모델이 편향에 기대는 정도를 따로 분석하지 않았다.
- **2-hop만**: 3·4-hop은 아직 다루지 않았다.

### 다음 단계

| 우선순위 | 작업 | 기대 효과 |
|---|---|---|
| ✅ | Multi-hop 검색 완료 (HoVer score 0.362 → 0.570, macro-F1 0.736 → 0.763) | - |
| 1 | **검증 모델 강화**: `deberta-v3-base`, `roberta-large`, MNLI로 학습된 모델, 검증 입력에 문장마다 제목 붙이기 | 이제 병목은 검증 모델 (근거를 찾은 claim에서도 약 0.80이 천장) |
| 1-1 | 후보 출처 ablation (claim 언급만 / 문서 본문 언급만) | multi-hop 효과와 개체 연결 효과 분리 |
| 1-2 | seed 여러 개로 반복, NFC 수정 후 베이스라인 재실행 | macro-F1 차이(+2.7%p)를 공정하게 확인 |
| 2 | NFC 수정 후 베이스라인(05~07) 재실행 | 공정한 비교 |
| 3 | 5단계 k=10으로 test 측정 | val에서 macro-F1 +3.6%p |
| 4 | 오류 분석 (틀린 주장을 맞다고 하는 오류, 놓친 근거) | 개선 방향 |
| 5 | 1차 후보 확대 (top-100), 반대 방향 링크 | 남은 검색 실패 |
| 6 | 3·4-hop 확장 | 프로젝트 목표 |

## 13. 예상 질문과 답변

**Q. 왜 공식 test가 아니라 dev로 평가했나요?**
공식 test는 라벨이 없어서 리더보드에 제출해야만 점수가 나온다. 공식 dev는 학습과 설정 선택에 쓰지 않고 최종 평가에만 썼고, 설정은 train에서 떼어 낸 val로 골랐다.

**Q. claim-only가 62%면 데이터에 문제가 있는 것 아닌가요?**
데이터에 편향이 있다는 뜻이다. 그래서 하한선으로 두고 근거의 효과를 그 위에서 쟀다. 근거를 다 찾은 claim(0.783)과 놓친 claim(0.694)의 차이도 모델이 근거를 실제로 쓴다는 증거다.

**Q. 왜 accuracy가 아니라 macro-F1인가요?**
train(SUPPORTED 72%)과 test(46%)의 분포가 반대라서, accuracy는 다수 클래스만 찍어도 높게 나올 수 있다. macro-F1은 두 클래스를 똑같이 평가한다.

**Q. 문서 검색에서 왜 precision이 아니라 recall인가요?**
엉뚱한 문서가 섞이는 건 문장 선택에서 걸러지지만, 정답 문서를 놓치면 뒤 단계에서 되돌릴 수 없다.

**Q. TF-IDF는 직접 만들었나요?**
아니다. HoVer 저자들이 DrQA로 계산해 공개한 top-100을 썼다. 원본 베이스라인과 같은 조건이다.

**Q. 왜 TF-IDF가 두 번째 문서를 못 찾나요?**
TF-IDF는 claim과 단어가 겹치는 문서를 찾는다. Bridge claim의 두 번째 문서는 이름이 claim에 없다. 실패한 claim의 85%가 한 문서만 찾은 경우였다.

**Q. Multi-hop 검색은 어떻게 두 번째 문서를 찾나요?**
두 곳에서 후보 문서를 모은다. ① 찾은 첫 문서의 본문에 등장하는 위키 제목(링크 따라가기, 연결형 claim에 효과적)과 ② claim 문장에 등장하는 위키 제목(이름이 claim에 있는데 TF-IDF가 놓친 비교형 claim에 효과적)이다. 그다음 claim과 첫 문서를 함께 보는 hop 2 모델이 후보마다 점수를 매기고, 경로 점수 P(첫 문서) × P(후보 | 첫 문서)로 문서 순위를 만든다. 두 출처를 합치면 한 문서만 찾은 claim의 79%에서 놓친 문서가 후보에 들어온다(① 52%, ② 44%).

**Q. "링크를 따라간다"는 게 무슨 뜻인가요?**
우리 위키 DB(`wiki_wo_links`)는 링크가 지워진 글자뿐이다. 그래서 글 속에서 대문자로 시작하는 구간이 위키 문서 제목과 정확히 같으면, 그 자리가 원래 링크였다고 보고 그 제목의 문서를 DB에서 꺼내 후보로 삼는다. 예: Marko Dmitrović 본문의 "SD Eibar" → `SD Eibar` 문서. "이름"은 사람뿐 아니라 팀, 나라, 작품, 연도처럼 위키에 문서가 있는 모든 대상이다. 관련 없는 이름도 함께 따라가며, 어느 문서가 필요한지는 hop 2 모델이 판단한다.

**Q. hop 1 문서 a₁, a₂에서 각각 몇 개씩 후보를 가져오나요?**
정해진 개수가 없다. a₁, a₂ 각각에 대해 **본문과 claim에 나온 위키 제목을 전부** 후보로 가져와 (a, c) 쌍을 만들고, 모든 쌍을 hop 2 모델로 점수 매긴다. 후보 수는 hop 1 본문에 위키 제목이 몇 개 나오느냐로 정해진다.

| hop 1 | 후보 (본문 + claim) | 쌍 |
|---|---|---|
| a₁ = Marko Dmitrović (본문 한 문장) | 10 + 6 = 16개 | 16쌍 |
| a₂ = La Liga (본문 김) | 약 100 + 6 = 약 106개 | 약 106쌍 |

claim에서 찾은 제목은 a₁, a₂ 양쪽에 들어가서 출발점만 다른 두 쌍으로 각각 점수를 받는다. test 전체로는 claim당 쌍 수의 중앙값이 약 200이다.

그다음 **a₁, a₂를 구분하지 않고** 모든 쌍을 경로 점수 P(a) × P(c | a) 하나로 줄 세운다. 최종 문서 목록에도 a₁, a₂ 몫이 따로 없어서, 상위 문서가 a₁ 쪽 후보로만 채워질 수도 있고 틀린 출발점(P(a)가 낮음)의 후보는 하나도 안 들어갈 수도 있다. 어느 hop 1이 맞는 출발점인지 미리 알 수 없으므로 몫을 고정하지 않았다.

| 단계 | 개수 | 코드 |
|---|---|---|
| hop 1 문서 | 2개 | `B = 2` (08) |
| (a, c) 쌍 | claim마다 다름 (중앙값 약 200) | 제한 없음 |
| 경로를 풀어 만든 문서 순위 | 20개 | `merge(..., k=20)` (08) |
| 문장 선택에 넘기는 문서 | 상위 5개 | `K_DOC = 5` (06) |

개선 여지: 후보가 많은 hop 1 문서(예: The Assignation 141개)는 계산 시간을 늘린다. a마다 후보 수 상한을 두면 빨라지지만, 그러려면 hop 2 모델 앞에 후보를 거르는 기준이 하나 더 필요하다.

**Q. 두 번째 문서가 첫 문서와 아예 관련이 없으면 어떻게 하나요?**
두 문서의 관계는 세 가지다.

| 관계 | 예시 | 지금 처리 | 결과 |
|---|---|---|---|
| ① 연결형: 첫 문서가 두 번째 문서를 언급 | Marko Dmitrović 본문에 "SD Eibar" | 링크 따라가기 | ✅ 찾음 |
| ② 비교형: 두 문서는 서로 무관하지만 이름이 claim에 다 나옴 | "José Echegaray와 Graham Swift 중 …" | claim에서 위키 제목 찾기 | ✅ 찾음 |
| ③ 반대 방향: 두 번째 문서가 첫 문서를 언급 | Goulburn 교도소 문서가 2014년 테러 진압 작전을 언급. claim에는 "The prison"뿐 | 없음 | ❌ 못 찾음 |

TF-IDF가 한 문서만 찾은 claim 386개 중 ①로 51.6%, ②로 43.5%, 둘 중 하나로 **78.8%**를 잡고, 나머지 **21.2%**(③과 이름이 다르게 쓰인 경우)는 지금 방식으로 찾지 못한다.

찾지 못해도 성능이 나빠지지는 않는다. hop 2 후보가 모두 엉뚱하면 점수가 낮게 나오고, 문서 순위를 만들 때 재정렬 순위와 번갈아 채우므로 **베이스라인이 찾던 문서가 남는다.** 결과적으로 이런 claim은 베이스라인 수준이 된다.

개선 방법:
- **역방향 링크(역색인)**: 위키 전체에 제목 매칭을 한 번 돌려 "이 제목을 언급하는 문서" 표를 만들고, 첫 문서를 언급하는 문서도 후보에 넣는다. ③을 잡는다. 모델은 그대로 쓴다.
- **재검색(BM25)**: "claim + 첫 문서 내용"으로 위키 전체를 다시 검색한다. 이름이 다르게 쓰인 경우까지 잡지만, 인덱스를 직접 만들어야 한다(공개 TF-IDF 결과로는 재검색 불가).
- **Dense retrieval(MDR 방식)**: 단어가 겹치지 않아도 의미로 찾는다. GPU 비용이 크다.

**Q. 왜 dense retrieval(MDR)을 쓰지 않았나요?**
520만 문서를 벡터로 만드는 데 GPU 시간이 많이 든다. 데이터 분석에서 놓친 문서의 대부분이 claim이나 첫 문서에 이름이 등장한다는 것을 확인했기 때문에, 더 가벼운 제목 매칭으로 먼저 효과를 확인하는 쪽을 택했다.

**Q. 문장 번호는 어떻게 맞췄나요?**
원본과 같은 CoreNLP로 문장을 나눴고, 정답 근거를 꺼내지 못한 claim이 0.2~0.3%뿐이라 번호가 맞는 것을 확인했다.

**Q. 결과를 얼마나 믿을 수 있나요?**
seed 하나로 한 번씩 돌린 결과라 몇 %p는 달라질 수 있다. 큰 결론(검색이 병목, 근거의 효과)은 차이가 커서 바뀌지 않는다. 또 NFC 버그로 검색 지표가 약 2%p 낮게 잡혀 있어 재실행 예정이다.

**Q. 3·4-hop은 언제 하나요?**
2-hop에서 multi-hop 검색의 효과를 확인한 다음이다. 그래야 점수 변화가 방법 때문인지 hop 증가 때문인지 구분할 수 있다.
